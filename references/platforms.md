# Platform Requirements

A skill supplies instructions; it does not grant image, edit, storage, account, or provider capabilities. Verify the live platform immediately before the task.

## Authorized target and native creator

Use only the agent and test scope authorized by the current assignment. Record changing rollout status outside the runtime instructions. Wider deployment requires Jack's approval after a verified one-agent result.

The current platform's native Skill Creator can govern authoring, structure and validation. That evidence does **not** establish an image-generation engine, image-edit capability, reference-image attachment, Drive binary upload, or file-readback capability. Check the current help for each actual action rather than extending creator evidence beyond what it says.

## Live-tool preflight

Before an image call, inspect current supported help/schema and record privately:

1. Which tool performs the image action and its actual image engine/provider.
2. Whether it accepts uploaded/reference image bytes, how many, and their accepted formats.
3. Whether it can create a **new scene** from separate images, and, if using the optional edit path, whether it can edit the supplied base image.
4. The actual input order/role mapping passed in the call and supported output handling.
5. Whether the executing agent's authorized file route can upload and read back an image binary.

State the image engine/provider separately from the agent's conversational model. A model used to write a prompt is not evidence that it generated the graphic. Do not invent a model name, runtime path, permission, command, mask, reference-strength setting, or preservation guarantee.

## Reference-input rules

New-scene generation requires actual supported image inputs, not text mentions of filenames. For the first Terry desk test, the exact three-image sequence is valid only if all three are actually attached in this order:

1. `office-main-desk.webp` — primary layout view.
2. `jack-standing-pointing-front.png` — body build.
3. `jack-portrait-pointing.jpg` — facial identity.

If the live tool cannot accept this required setup, stop and report the specific gap. Do not replace it with a generic Jack description, a private file link, a different unvalidated provider, or a supervisor-generated image.

For ordinary tasks, select the needed environment, face, and body inputs within the confirmed limit, declare their actual roles, and choose one camera/layout authority. Environment-first and character-last wording is a call record, not a claim to make when the attached order differs.

## New scenes and edits

Reference-based new scenes are the core route. They must be tested as new scenes from separate inputs, including structural visual checks.

Editing a suitable approved scene is optional for a small change only. Use it only after confirming real edit support for the actual base image. An edit result does not validate new-scene generation. Do not depend on undocumented masks, selective-region controls, strength settings, or a text-only promise of pixel-perfect preservation.

## Provider, saving, and failure boundaries

Use the existing approved route only. Do not quietly swap provider/image engine, change an agent's default model, install a runtime, add credentials, create an OAuth connection, or buy a service to obtain an output. A different engine is not prohibited forever; it remains unvalidated until Jack approves and tests that route.

Make one initial output and, if justified, one focused correction. On broad identity/layout failure, missing capability, or persistent material defect, stop and report the facts. Do not represent a prompt, a local file, or another agent's result as the executing agent's successful test.

Keep image binaries, private folders, account IDs, upload receipts, and private payload locations out of repository files and public logs. A passing result still requires the approved binary upload and independent read-back; otherwise report it as `not-saved`.
